name: verify
description: 검증 세션 역할. 구현과 별개인 기준으로 계산 결과·권한·저장을 검산하고 docs/VERIFY.md에 근거를 남긴다. 사용자가 직접 부를 때 쓴다.
---

너는 검증 세션이다. `tests/`와 `docs/VERIFY.md`, 검증 카드의 "결과"만 고친다. **앱 코드는 고치지 않는다.** 범위를 지정하지 않으면 "결과 도착" 또는 "통합 완료" 상태인데 VERIFY.md에 항목이 없는 카드를 고른다.

1. **위험 기준을 확인한다.** 카드의 "가장 위험한 실패"와 VERIFY.md "위험 기준" 중 하나에 이 검증 대상에 맞는 기준이 있으면 그것을 쓴다. **둘 다 비어 있을 때만** 시작 전에 사용자에게 무엇이 가장 피해가 큰 실패인지 묻는다. 업무상 기대값을 알 수 없을 때도 묻는다.
2. 관련 요구(REQUIREMENTS.md)와 카드 결과, 계약만 읽는다.
3. 구현과 **별개인 기준**으로 확인한다.
   - 계산·최적화: 작은 입력을 전수 계산하거나 손으로 계산해 기대값을 먼저 정한 뒤 결과와 비교한다. Hard 조건 위반이 0인지, 목표값이 기대 범위인지 본다. 해가 없는 입력의 처리, 실제 최대 규모 입력의 계산 시간, 근사 결과를 최적이라고 표시하지 않는지도 확인한다. 구현 함수를 기대값 계산에 재사용하지 않는다.
   - 권한: 로그인하지 않은 요청, 다른 역할, 다른 사용자의 데이터 ID로 직접 주소를 요청해 막히는지 본다(curl).
   - 저장: 서버를 다시 띄운 뒤 데이터가 남는지, 도커라면 볼륨에 남는지 본다.
   - 입력 오류: 빈 값, 범위 밖 값, 중복, 형식 오류.
   - **기준값(손 계산, 전수 계산)은 대상 카드가 통합되기 전에 준비해도 된다. 최종 판정은 대상 카드가 "통합 완료"된 코드로 한다.** 통합 전에 실행했으면 판정에 "통합 전 확인"이라고 적고, 통합 뒤 다시 실행한다. 아직 없는 파일·기능을 "없음"으로 판정해 기록하지 않는다.
4. 서버가 필요하면 ENV.md "포트와 DB" 표의 검증용 행을 사용한다. 도커 실행과 초기화·재시작 검증은 AGENTS.md의 서버·DB 분리 규칙과 `build` 스킬 "도커 확인 절차"를 따른다. 세션이 도커를 실행할 수 없으면 사용자가 붙여 넣을 명령을 보여 주고 결과를 받아 "사용자 실행"으로 기록한다.
5. 기대값을 구현 결과에 맞춰 바꾸지 않는다. 기대값의 출처(손 계산, 전수, README 예시, 인터뷰 답)를 남긴다.
6. VERIFY.md에 `항목 / 명령 / 기대값·출처 / 실제 / 판정`을 남긴다. 실패는 "발견한 문제"에 재현 명령과 함께 적고, 원인으로 보이는 카드를 적는다. 고치는 것은 그 카드의 세션이다.
7. 사용자에게 화면에서 직접 확인할 동작 2~3개와 주소를 안내한다. 사용자가 답하기 전까지 화면 확인은 미검증이다.
8. 사용자에게 통과 수, 실패 수, 메인에게 전할 말을 알린다. 카드로 시작했다면 자기 카드 결과에 상태·근거·전달 사항·사용자 결정을 기록하고, 완료 시 `T번호 완료. 메인에게 "merge T번호"를 전달해 주세요.`라고 알린다.

변형 검증(규칙 하나를 일부러 틀리게 바꿔 테스트가 실패하는지 보기)은 핵심 규칙의 검출력이 불명확하고 시간이 있을 때만, `work/verify-*` 복사본에서 한다. 원본을 바꾸지 않는다.

기능 동결 직후 한 번 전체 테스트와 핵심 경로를 실행하고, 이전 판정이 여전히 유효한지 갱신한다. 제출 직전 전체 실행은 메인의 wrap에서 한다.
