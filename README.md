# Codex 작업 하네스 (본선판: 여러 세션 분업)

제한 시간 안에 업무 과제의 필수 요구를 놓치지 않고, **여러 Codex 세션이 역할을 나눠** 실행 가능한 결과물을 만든 뒤, 사용자가 판단 이유와 검증 근거를 직접 설명하기 위한 하네스다. 과제 README와 작업 플랫폼의 실제 안내가 우선한다.

예선용 단일 세션 버전은 [hekate-louise/codex-harness](https://github.com/hekate-louise/codex-harness)의 `main` 브랜치와 `exam-2026-10-31` 태그에 있다.

## 설치
과제 루트에서 실행한다.

```bash
git clone https://github.com/hekate-louise/codex-harness-final /tmp/h && bash /tmp/h/install.sh .
```

`/tmp`에 쓸 수 없으면 `work/codex-harness-final`에 받는다(`work/`는 커밋 제외).

```bash
git clone https://github.com/hekate-louise/codex-harness-final work/codex-harness-final && bash work/codex-harness-final/install.sh .
```

설치기는 AGENTS.md, `REPORT.md`, `docs/` 문서 틀, `orch/` 폴더, 스킬을 복사한다. 이미 있는 파일은 덮어쓰지 않는다. 설치한 뒤 Codex를 다시 시작한다.

## 핵심 생각
- **지휘자는 사용자다.** 세션은 서로 직접 말하지 않고, 사용자가 터미널마다 일을 맡긴다.
- **파일로 소통한다.** 메인이 작업 카드(`orch/T번호-….md`)의 "지시"를 쓰고, 맡은 세션이 "결과"를 쓴다.
- **한 파일은 한 역할만 고친다.** 병렬 작업끼리 충돌하지 않게 하는 가장 중요한 규칙이다.
- **뼈대 먼저, 그다음 분업.** 공통 계약(DB 구조, 주소, 역할·권한, 파일 담당)과 실행되는 뼈대가 없으면 병렬 작업은 서로 어긋난다. 뼈대(T01)는 구현 세션이 만들고, 메인은 코드를 쓰지 않아 긴 경기 동안 컨텍스트를 아낀다.
- **진행 상황의 원본은 `docs/PLAN.md` 하나.** 메인만 고친다.

## 역할과 터미널
| 터미널 | 역할 | 시작 | 언제 띄우나 |
|---|---|---|---|
| 1 | 메인 | `$main` | 처음부터 끝까지 |
| 2 | 인터뷰 | `$interview` | 처음 30분. 이후 답이 올 때마다 |
| 3 | 구현 A | `$build T01` (뼈대) → `$build T03` | 계획 승인 직후 |
| 4 | 구현 B | `$build T02` (최적화 계산) → `$build T04` | 계획 승인 직후 (T01과 동시) |
| 5 | 학습 | `$explain` | T01이 도는 동안부터. 모르는 개념이 나올 때마다 |
| 6 | 디자인 | `$design` | 사양은 T01 동안, 적용은 뼈대 완성 뒤 |
| 7 | 검증 | `$verify` | 최적화 카드가 시작되면 기준값 준비, 이후 카드가 끝날 때마다 |
| 8 | 문서 | `$docs` | 통합이 몇 번 쌓인 뒤 틈틈이 |
| + | 셸 | (Codex 아님) | 커밋, 서버 확인용 |

처음 1시간은 메인과 인터뷰만으로 시작하고, 나머지는 할 일이 생길 때 연다. 사용자에게 몰리는 질문과 보고는 메인에게 `상태`를 입력해 한 번에 모아 처리할 수 있다. 구현 외 역할은 한 번에 한 세션만 띄운다.

세션 수는 제한하지 않는다. **구현·검증·디자인 세션은 메인이 카드를 만든 뒤에 그 카드 번호로 명령한다.** 결과를 제때 읽지 못할 만큼 쌓이면 세션을 늘리지 않는다. 무엇을 어느 터미널에 입력할지는 메인이 매번 알려 준다. 한 터미널을 역할만 바꿔 다시 쓸 수 있다(새로 열고 `$handoff`로 받은 인계 문서를 읽힌다).

## 시간 흐름 (09:30~16:00, 약 6시간 반 기준)
| 구간 | 메인 | 다른 세션 |
|---|---|---|
| 0:00~0:30 | README 읽기, 환경 점검(ENV), 요구사항 초안 | 인터뷰: 1차 질문 초안 / 학습: 업무·알고리즘 개념 정리 |
| 0:30~1:00 | 공통 계약, 계획, 카드 분할 → **사용자 승인** | 인터뷰: 답 기록 |
| 1:00~1:45 | 인터뷰 답 반영, 다음 카드 다듬기, T01 통합. 1:45에 뼈대가 안 되면 범위 축소를 사용자에게 물음 | **구현 A: T01 뼈대**(로그인 + 최소 흐름 하나) / **구현 B: T02 최적화 계산**(순수 함수와 테스트) / 학습: 데이터 흐름 설명 / 디자인: 화면 사양 / 검증: 전수 계산 기준값 |
| 1:45~5:00 | 카드 통합, 보드 갱신, 커밋 안내 | 구현 A·B, 디자인, 검증, 문서 병렬 |
| 5:00 | **기능 동결 기준**: 메인이 남은 Must와 진행 카드를 보여 주고, 사용자가 동결할지 정한다 | |
| 5:00~6:15 | 통합 실행, 도커, 최종 점검(`$main wrap`) | 검증: 전체 재확인 / 문서: REPORT·발표 원고 / 학습: 이해도 점검 |
| 6:15 (마감 15분 전) | 제출물 확정 목표 | |

시간은 판단 기준이다. 실제 시작·마감 시각은 사용자가 알려 주고 메인이 PLAN.md에 적는다. 점심(12:00~13:00) 동안에도 경기가 이어지는지 현장 안내를 확인한다.

## 문서 지도
| 파일 | 담당 | 내용 |
|---|---|---|
| `REPORT.md` | 문서 | 결과 보고(제출용) |
| `docs/PLAN.md` | 메인 | 시간 기준, 공통 계약, 카드 보드, 진행 기록 |
| `docs/REQUIREMENTS.md` | 메인 | 요구사항, 상태, 검증 연결 |
| `docs/ENV.md` | 메인 | 기술 스택, 실행 명령, 포트, 테스트 계정, 도커 |
| `docs/DECISIONS.md` | 메인 | 중요한 선택, 이유, 버린 대안 |
| `docs/INTERVIEW.md` | 인터뷰 | 질문 초안, 받은 답, 영향 |
| `docs/STUDY.md` | 학습 | 사용자가 배운 개념, 예상 질문 |
| `docs/VERIFY.md` | 검증 | 검증 명령, 기대값, 실제값 |
| `docs/DESIGN.md` | 디자인 | 수치로 된 화면 사양 |
| `docs/DATA.md` | 문서 | 데이터 흐름 표(만드는 곳·원본·읽는 곳·수정 권한) |
| `docs/PITCH.md` | 문서 | 2분 발표 원고, 시연 순서, 예상 질문 |
| `docs/REVIEW.md` | 문서 | 요구사항 대비 누락 감시 메모 |
| `orch/` | 메인(지시)·각 역할(결과) | 작업 카드, 인계 |

과제가 같은 역할의 파일을 지정하면 그 파일을 쓰고 PLAN.md에 경로를 적는다.

## 스킬
| 스킬 | 역할 |
|---|---|
| `main` | 시작(`start`), 카드 분할(`cards`), 새 결과 모아 보기(`상태`), 통합(`merge 카드번호`), 막힌 카드 처리(`카드번호 막힘`), 결정 기록·상의(`카드번호 결정 반영해` / `카드번호 결정 필요`), 마무리 점검(`wrap`) |
| `build` | 카드 하나 구현(`$build T03`). 도커 예시 파일(`docker/`) 포함. 막힌 카드는 카드의 원래 역할로 이어받는다(`$build T03 막힘`, `$verify T05 막힘`, `$design T02 막힘`) |
| `verify` | 독립 검산, 권한 우회 시도, 최종 재확인 |
| `design` | 수치로 된 화면 사양을 먼저 쓰고 스타일 적용 |
| `interview` | `check`: 질문 점검 / `record`: 답 기록 |
| `explain` | `learn`: 개념 배우기 / `check`: 예상 질문, 피드백, 모범 답안(문항 수 제한 없음) |
| `docs` | REPORT, 데이터 흐름 표, 발표 원고, 누락 감시 |
| `handoff` | 같은 역할 세션 교체 시 인계 |
| `frontend-design` | 업무 화면 디자인 기준(`design-reference.md`). 디자인 역할이 읽는다 |
| `impeccable` | 화면 점검 지침(문서판, 실행 파일 없음). 예: `$impeccable critique static/index.html` |

## 속도와 사용량
- 예선에서 Codex가 느렸던 주원인은 fast 모드를 쓰지 않은 것으로 보인다. 시작할 때 fast 모드와 모델 설정을 확인한다.
- 여러 세션은 시간을 줄이지만 사용량을 늘린다. 할 일이 분명한 세션만 띄우고, 끝난 세션은 닫는다.

## 하네스가 스스로 정한 원칙
화면 자동 조작 없이 터미널·HTTP 검증과 사용자의 화면 확인을 조합한다. 과제 데이터를 외부로 보내지 않는다. 커밋 제안은 메인만 하고, 커밋은 사용자가 로컬에서 한다. 웹 서버는 0.0.0.0에 바인딩한다. 시간 배분과 세션 수는 운영 전략이며 성능을 보장하지 않는다. 응시 규정은 플랫폼 안내를 따른다.
